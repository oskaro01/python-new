# Django Basics 27: Render + Neon Deployment Preparation

This lesson prepares the Personal Dictionary for deployment. We will use:

```text
GitHub -> Render web service -> Neon PostgreSQL -> Gunicorn -> HTTPS
```

We are preparing the deployment files, but we do not publish automatically.

## Why This Setup?

Render is a good home for the Django web service because it supports:

```text
Django web service
environment variables
automatic builds from Git
HTTPS
```

Neon provides the separate PostgreSQL database. This keeps the database
independent from the Render web service and avoids relying on Render's
temporary free database offering.

The free tiers are suitable for learning, but their limits and terms can
change. Keep CSV or JSON backups of important dictionary data.

## Files

### `requirements.txt`

Production packages:

```text
Django
dj-database-url
Gunicorn
psycopg
WhiteNoise
```

### `build.sh`

Render runs this during deployment:

```text
install packages
collect static files
apply migrations
```

### `.python-version`

Keeps deployment on Python `3.12.10`, matching our local environment.

### `render.yaml`

Describes only the Render web service. `DATABASE_URL` is marked `sync: false`
because we will paste the Neon connection string into Render manually.

## Local Vs Production

Locally, without `DATABASE_URL`, Django uses:

```text
SQLite -> db.sqlite3
```

In production, with `DATABASE_URL`, Django uses:

```text
PostgreSQL -> Neon
```

Static files use:

```text
local: Django development static serving
production: collectstatic + WhiteNoise
```

## Deployment Steps

### 1. Commit And Push

Commit the deployment files and push the repository to GitHub.

Never commit:

- `.env`
- database passwords
- secret keys
- local `db.sqlite3`

### 2. Create A Neon Database

1. Create a Neon account and project.
2. Create or select the database for this project.
3. Copy the PostgreSQL connection string.
4. Keep the connection string private.

We will use that value as Render's `DATABASE_URL`.

### 3. Create The Render Web Service

1. Open Render.
2. Choose **New Blueprint Instance**.
3. Connect the GitHub repository.
4. Let Render read the root `render.yaml`.
5. Apply the blueprint.

This blueprint creates the web service only. It does not create a Render
database.

### 4. Add Environment Variables

In the Render service settings, add the Neon connection string:

```text
DATABASE_URL=your-private-neon-postgresql-connection-string
```

Set these values after Render gives the service its `onrender.com` hostname:

```text
DJANGO_ALLOWED_HOSTS=your-app.onrender.com
DJANGO_CSRF_TRUSTED_ORIGINS=https://your-app.onrender.com
```

`DJANGO_SECRET_KEY` is generated by the Blueprint. Keep it secret.

### 5. Confirm The Database Before Deploying

Do not deploy the web service until `DATABASE_URL` contains the Neon
connection string. Otherwise Django may start with the wrong database
configuration.

The build script will then run migrations against Neon:

```text
python manage.py migrate
```

### 6. Create The First Admin User

After deployment, open the Render Shell and run:

```bash
python manage.py createsuperuser
```

Then open:

```text
https://your-app.onrender.com/admin/
```

### 7. Check The Live App

Verify:

- the home page loads
- CSS appears
- registration works
- login works
- words save to Neon PostgreSQL
- admin opens
- password reset email configuration is set before relying on it

## Production Start Command

Render does not use Django's development server. It runs:

```bash
gunicorn mini_site.wsgi:application
```

`mini_site/wsgi.py` exposes the `application` object Gunicorn needs.

## Important Database Rules

- Do not upload the local SQLite database.
- Do not paste the Neon connection string into Git files.
- Do not use a temporary Render database as the only copy of your data.
- Keep CSV or JSON backups before major changes.
